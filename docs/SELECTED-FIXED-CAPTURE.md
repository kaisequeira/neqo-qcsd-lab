# FRONT and BuFLO for selected sites

The selected-site ledger keeps the earlier admitted class identities and adds
new classes without replaying every earlier site's GET. This extension lets its
new group of 1–5 sites use the existing fixed FRONT V4 or BuFLO 200-second setting.
The target remains 50 classes × five settings × 64 visits: 16,000 formal traces.

## What changes before capture

Each setting gets a new declaration and derived workload files. Every resource
occurrence, dependency, request header, approved origin and original GET identity
stays unchanged. The derived files add only the separately typed capture role
and the declared FRONT or BuFLO preparation policy. Class indices and earlier
formal evidence stay in their original ledger and measurement epoch.

If the current selected-input validator differs from the validator recorded in
an older receipt, the amendment publishes a new current receipt from the same
retained selection audit and complete raw GET. It independently checks that raw
evidence; it does not visit the website again or rewrite the older receipt.
The declaration records both the old input and its current receipt.

The amendment binds the actual current Source, client, image, fixed traffic
files, exact enrolled group and its original response/recording limits. A group
must retain one set of limits. BuFLO explicitly selects the existing duration-200
parameters and their provenance; it uses the existing mode-specific deadline.
No fitting or new Native feature is introduced.

## Use the portable flight command

Follow [the flight guide](RAPID-CLASS-MODE-FLIGHT.md), using the selected ledger's
study root and enrollment. Supply a genuinely installed current runtime and a
fresh output directory. Choose `--mode front` or `--mode buflo`.

Run `stage`, `amend`, and `finalize`, then the recorded `preamble`, `qualify`,
`preflight`, `capture`, `deep`, `readiness`, and `plan` steps. The public `amend`
command chooses this new contract only for the typed selected enrollment.
The default three selected settings keep their existing contract.

Both amended settings require response-only qualification that starts after
their declaration, followed by their own full-graph canary and independent deep
verification. An old named group whose base manifests have different bytes
cannot be reused as qualification for the new derived manifests. Successful
canaries and input renewals add no formal trace credit.

This extension supports serial lanes and their existing failed-lane recovery.
It rejects selected-site parallel capsules and historical canary Source
projection. Parallel support needs a separately authenticated scheduling
contract. HOST fixtures validate control and raw-evidence contracts; they do
not prove installed or live FRONT/BuFLO capture viability.
