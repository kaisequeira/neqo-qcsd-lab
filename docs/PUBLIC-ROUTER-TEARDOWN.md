# Completed router teardown

A completed capture can remain valid while its host launcher fails during
Docker cleanup. The capture's sealed evidence and ordinary deep verification
describe the trace; the launcher's exit status and lifecycle records describe
whether its router and network were retired. Report both outcomes separately.

The prospective launcher gives a completed public or parallel topology's exact
container/network removal one bounded 30-second allowance. Killing a router
and detaching its network can exceed the three seconds used for identity
queries. The removal remains one request inside the existing authenticated
service. Its source and daemon checks are retained, followed by exact absence
proof and HANDOFF retirement. An API failure still fails cleanup, including a
failure returned after the daemon removed the object.

Failed launch cleanup and cleanup after a terminal signal keep the three-second
API bound. Dedicated ordinary identity/absence services retain their existing
three-second bound. Inside a completed 30-second removal service, the fresh
daemon identity check retains the host Python helper's existing 10-second
internal bound. The supervisor's 120-second terminal-signal envelope is
unchanged. If a signal
arrives after a completed removal has already started, that request retains
its bounded allowance; subsequent cleanup requests use the short bound.
No retry is added to a mutation. General Docker calls, builds, controlled
topologies, traffic settings, qualification checks and the Native client are
unchanged.

This is a prospective source change. Keep running checkouts and old attempted
evidence immutable. Publish and bind a new launcher/runtime before using this
behaviour; existing exact source checks still apply. An old failed host exit
does not become a successful exit after publication. Standard lifecycle
recovery can close its retained cleanup state under that unchanged old source.
The current collector runtime compatibility bridge still protects launcher
identity and rejects this launcher change; this repair does not expand that
bridge or reuse a historical qualification under a changed launcher.

The focused shell tests exercise slow removal, failures, missing absence proof,
failed HANDOFF retirement and terminal signals. They replace the Docker service
boundary with a bounded local process; an actual installed runtime rehearsal
is still required before claiming live teardown success.
