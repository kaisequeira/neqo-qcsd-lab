# Capture working classes without waiting for the whole candidate list

This is a prospective serial study path. A working class can be added after
its complete ordinary GET has genuinely passed, even while earlier candidates
remain unassessed. It does not declare those candidates failed or finished.

## What stays as evidence

The original acquisition records, class numbers, sources and sample identities
keep their original meaning. Creating the new policy audits the existing
enrollment through its explicitly supplied, unchanged original source checkout.
It retains that operation's command, source metadata, exit status and raw logs.
It also links the existing independently verified formal-sample counter.
These steps add no samples to that counter.

Each selected class gets an independent capture-input receipt. It retains the
full resource list, repeated requests, headers, dependency edges, approved
origins, primary HTML response, bootstrap and complete GET records, response
body hashes, DNS, HTTP/3, endpoint completion, original source and client labels,
and declared limits. The ordinary primary response may vary during capture
under the existing response policy. Auxiliary response identities still have
their existing exact checks.

During a trace check, the selected receipt reconstructs that class's own raw
GET evidence. Enrollment checks its immutable membership and linked selection
audit metadata. It does not repeat every earlier candidate's failed or partial
GET. Altered selected raw bytes, modes, directory membership, graph rows,
source files, caps or audit records still reject the input.

## Membership and pending candidates

The new policy copies the existing class mapping as its seed. Actual deployment
must use the latest genuine enrollment and independently verified sample anchor.
The first new batch continues the old batch numbering in a fresh policy
namespace. Classes are appended; existing class numbers are never reassigned.

Within each batch, explicitly supplied, genuinely admitted candidates are
sorted by their declared reservation order. Every other declared reservation
is recorded as `unassessed-by-this-ledger`, without a fabricated terminal.
An earlier pending candidate may join a later batch after its own successful
GET. Previously selected classes keep their numbers and earlier receipts keep
their bytes. Duplicate candidate IDs, workload IDs, canonical primary hosts
and class numbers are rejected. The target remains 50 classes × 5 settings ×
64 visits = 16,000 traces.

## Public commands

Use the project Python environment and the published source checkout. All
paths are explicit inputs; the tools contain no fixed machine, site or runtime
identity. Outputs must use fresh, unused locations.

1. Run `tools/rapid_selected_capture_input.py audit-enrollment` with the original
   source checkout, its source manifest, genuine seed enrollment and a fresh
   audit output directory. For later admissions use `audit-static-terminal` or
   `audit-whole-terminal` with the genuinely admitted terminal and its context.
2. Run `publish-input` once per selected candidate using that audit, followed
   by `prepare-input`. The prepared manifest retains every original graph row
   and declares the new selected-input role explicitly.
3. Run `tools/rapid_additive_static_enrollment.py initialize` with the seed
   enrollment, its audit, candidate-to-input JSON map, existing sample anchor
   and actual current runtime specification. The policy directory must exist
   and be empty. Then run `enroll` with candidate-to-input and
   candidate-to-prepared-manifest JSON maps. Maps accept absolute paths or
   exact path/hash/mode references.
4. Use `tools/rapid_class_mode_flight.py` for that new enrollment and matching
   installed runtime. Complete the setting's actual named response qualification,
   complete-site canary, deep verification and readiness. Then publish the
   ordinary serial rolling plan and launch its lanes through
   `tools/rapid_rolling_capture.py`.

Each CLI's `--help` lists its required arguments. An old qualification or canary
is not promoted to the new scientific role. The current implementation permits
fresh undefended, Tamaraw and CS-BuFLO serial flights independently.

## Remaining separate work

Selected FRONT V4 and BuFLO V12/200 need their own explicit prospective fixed
policy declaration. Importing an older static amendment is rejected. Selected
parallel scheduling also needs a separately authenticated authority. These
requirements do not prevent a ready supported serial setting from capturing.

Final accounting across old and new policies needs a typed mixed-policy
corpus integration. The existing final-corpus checker is not claimed to accept
this new ledger yet. Its mapping must preserve original sample identities and
use each registered block plus raw local visit for later samples:
`logical_visit = (registered_block - 1) * 4 + actual_local_visit`.
Retry generations keep the same logical slot; raw samples are never rewritten.
The linked existing counter is provenance, not new scientific credit.

The new selected role currently supports complete original-budget static and
whole graphs. A response-budget successor is a distinct role requiring its own
explicit support. There is no installed selected-role success claim from HOST
fixtures alone.
