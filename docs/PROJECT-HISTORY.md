## Reading the record correctly

Three categories are deliberately kept separate:

- **Scientific evidence** is an accepted, sealed result for the exact source,
  image, parameters, workload and protocol recorded by its receipt.
- **Engineering evidence** includes tests, probes, incomplete prefixes, failed
  executions and observations that found or repaired a defect. It can justify
  a design change but cannot advance a scientific numerator.
- **Operational state** describes processes, Docker objects, host epochs and
  recovery decisions. It neither validates nor invalidates an algorithm by
  itself.

The wording “five validated defences plus two candidates / nine selectable
modes” remained the correct claim at this snapshot. BuFLO and CS-BuFLO had not
passed the final validation attestation. The extended study remained at pilot
classes 0/120, final classes 0/100, certification 0/900 and formal capture
0/16,000. Browser-vector passes and timing attempts are prerequisites or
engineering evidence; they are not class acquisitions or traffic-capture
samples.

## Candidate timing lineages v103–v116

Timing stress is intentionally earlier than the large compatibility matrices.
It asks BuFLO to sustain a strict 100-second prefix: 5,001 opportunities per
direction, including tick zero, with kernel transmission evidence and an
independent router-ingress match. Terminal drain is bounded by 6,000
opportunities per direction. One first-launch failure consumes that cell;
there is no substitution. These runs diagnosed the precise late path rather
than waiting for a 900-cell certification run to expose it.

## V116 interruption and host-epoch interpretation

The immutable recovery record bound the interrupted execution to host boot ID
`1cd1fc9f-d086-4948-bd97-5dc8b1d950e1`. On 25 September the observed host and
`docker-desktop` boot ID was
`1e137b41-59c2-42e0-bb2b-1dee2af249d7`, so a full host epoch change had
already occurred. The Docker server identity remained
`48f27adb-00f1-41ce-80fe-41360d2eb712`, with root `/var/lib/docker` and live
restore disabled. The exact v116-labelled network persisted empty, the
intended target container was absent, and all inspectable retained containers
had restart policy `no` and restart count zero.

This observation permits only a cautious operational conclusion. An
unchanged-source state-retaining resume on a changed daemon process can be
scientifically considered only when the host-epoch change is receipted, the
persistent Docker server ID/root and exact prior object remain identical, and
the target is demonstrably absent. The current boot ID, daemon PID/start
identity and observation time must be regenerated. A changed Docker server
ID, root, object state or source requires the incomplete v116 evidence to be
preserved and a fresh cohort to start. The 25 September migration chose the
conservative path: preserve v116 unchanged as an incomplete laptop execution,
do not promote or resume it on the desktop, and establish fresh native
authority there.

## Migration decision on 25 September

The approved plan moves future collection from the ARM64 laptop environment
to native amd64 Ubuntu under WSL2 on a stronger desktop. Desktop restoration
and native qualification had not yet been performed. The decision was an engineering reset, not a
scientific result and not a reinterpretation of old receipts.

- Git carries source, checked-in specifications and tracked documentation.
- The protected handoff, all local artifacts, pinned reference inputs and
  unique research material travel through the checksum-governed migration
  bundle.
- Historical raw result trees remain on the laptop research archive and must
  be retained through thesis submission.
- Build targets, environments, caches, graph indexes and Docker state are
  regenerated; sessions, credentials and machine-specific instructions are
  not committed.
- The desktop requires a native pinned-browser profile, fresh no-cache build,
  host and timing qualification, 110-vector browser gate and all later
  authorities. ARM64 browser evidence does not authorise amd64 execution.

The operational sequence was also changed to fail cheaply: focused source and
synthetic consumer tests, then host/ETF/veth and targeted browser lifecycle
diagnostics, then the expensive clean build and browser suite. Public
acquisition may begin after the narrower acquisition authority; the complete
reference/timing/regression/code/controlled foundation remains mandatory
before class-study fitting or any defence capture. This supersedes historical
runbooks that required the full defence foundation before public acquisition,
without weakening the prerequisites for fitting, certification or formal
capture.

## Historical claim boundary at migration

### Native desktop preparation implemented on 25 September

The migration implementation added an independent amd64 browser profile for
Playwright 1.57.0 / Chromium 143.0.7499.4, revision 1200. Offline audits verified
the official archive, executable, extracted distribution and locked Playwright
wheel before and after the existing ownership patches. The amd64 archive is
Chrome for Testing: its `chrome-linux64` root is normalised to the established
runtime path, and its distinct managed-policy directory is used by both image
packaging and positive-control qualification. Historical ARM64 identities are
unchanged.

Docker selection, pinned-CDP, browser qualification, acquisition and the
independent watcher were updated together. Portable verification selects the
profile from hash-bound build architecture rather than the verifier's host.
Local tests exercise profile mismatches, historical replay and synthetic
receipt closure. Review also caught two incomplete integration points before
publication: the final CDP observation still defaulted to ARM, and the
validated-build projection omitted architecture; both were corrected and
focused tests passed. Existing stale launcher fixtures were reconciled with
the already-present ETF/veth and teardown interfaces without changing runtime
timeouts or acceptance.

The evidence transfer was checked by full round-trip download hashes and a
fresh local extraction rehearsal, including all 12,503 classifier checksums.
These are migration/engineering checks only. No native amd64 executable,
desktop image, timing gate or live browser qualification was run on the ARM
laptop, and no scientific counter advanced.

## Maintenance contract

Future maintainers should append a dated, evidence-backed outcome after each
terminal milestone. Record the exact source/Gitlink, receipt or result path,
whole-file hash, accepted numerator and supersession reason. Preserve failed
attempts and operational failures. Never upgrade old evidence because current
source contains a fix, and never report a partial browser prefix, timing probe
or local test as a class/capture result.

The portable appendices above are frozen after this migration. If a thesis
audit needs an old ignored artifact, retrieve the complete object from the
location described in the [evidence index](EVIDENCE-INDEX.md) and verify its
closed inventory before use. The external migration bundle retains the exact
pre-migration source bytes; tracked historical copies are portable
representations whose transformations are exhaustively recorded in the
[source map](HISTORY-SOURCE-MAP.md).
